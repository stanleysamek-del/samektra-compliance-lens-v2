# Compliance Lens: equipment scanning, reliability, and paid AI

Prepared September 8, 2026. Changes are local in `D:\samektra-compliance-lens-v2`. No live database migration, deployment, payment activation, or paid model request was performed.

## What is ready in this release

- Equipment register with exact barcode matching inside a selected building. Camera and image scanning support common 1D formats and QR codes. Leading zeros are preserved; QR URLs are treated as identifiers, never navigated to. Camera failure offers image/manual alternatives, and camera sessions stop after 60 seconds.
- Local CSV/TSV, XLSX, and text-PDF equipment import. Select building, sheet/page and header row; map columns; review/edit/remove rows; explicitly confirm the import. Existing barcodes are skipped unless updating is selected. An update preserves equipment IDs, check history, due dates, status, and floor-plan pins. Blank fields do not erase metadata. Up to 500 rows per import, 20 MB source file, and 100 PDF pages. Manufacturer/model/serial/location are supported. A CSV example is available at `/equipment-import-template.csv`.
- Equipment plan placement with a preview and confirmation. Subsequent scans open the same equipment record and its saved plan position. Database checks reject cross-building placement, duplicate device pins, invalid coordinates, and building changes that would invalidate existing pins. Importing a text location does not guess a floor or coordinates.
- Equipment checks with dated pass/fail/not-tested history and next due date. Failed/not-tested checks require a note. A not-tested check does not reset the due date. These are generic equipment checks, not a complete certified extinguisher maintenance procedure.
- Repeat inspection schedules with daily/weekly/monthly/quarterly/annual cadence. Starting a due occurrence copies questions and sections with fresh answers. Duplicate starts return the same inspection; month-end dates retain their anchor. Due rounds are started by the user, not automatically generated by a new cron.
- Manual photo capture is the default. Guests get the free prepared demo; free accounts retain manual workflows. Barcode/report parsing is local and makes no paid provider call. Viewers cannot mutate shared inspections or use their organization's paid AI.
- Server-verified paid entitlements, atomic usage reservations, monthly credits and spending ceiling, and a rolling 24-hour global ceiling. No signup grants paid usage. Pro permits standard analysis/coaching; Facility/Healthcare also permit advanced review. Payment activation is operator-managed until a verified checkout/webhook integration is built.
- Standard analysis tries configured Google Flash first, then Haiku, then the existing OpenAI fallback. Explicit `AI_PROVIDER` wins. Advanced escalation is limited to eligible paid plans and remaining time/budget. Missing evidence does not trigger escalation. Provider attempts share a time budget; ambiguous failed-call costs retain budget holds.
- Analysis saves are transactional, reject stale replacements and finalized inspections, preserve edited/assigned/linked findings, and do not auto-resolve missing evidence just because AI omits it. Completed job replay avoids another provider call. A retired upload action that bypassed the budget check is disabled.
- Self-promotion through `profiles.is_admin` is blocked for browser roles. Finalization is blocked at the database boundary while photos/jobs are unfinished. Updated framework/image dependencies and patched transitive packages. PDF rendering uses the installed local worker; the CDN script/worker exception was removed from CSP.

Do not reset production, use seeds, or repair migration history blindly. With CLI-managed history, inspect `supabase migration list` and the `supabase db push --dry-run` output before applying. If you normally use the SQL editor, run the complete files in order and keep an application record; do not mix untracked SQL-editor changes with assumed CLI history.

For production, take/verify a recoverable backup, pause the old AI worker and temporarily disable its provider credentials, apply the tested migrations, then deploy this matching application version and restore the selected provider configuration. Setting the new budget variable on an old app is not sufficient because the old code did not enforce it. Never roll back to the old application while paid keys are enabled: that would restore its budget bypass. If the new release fails, leave paid AI disabled and fix forward; do not drop tables containing new customer records.

## Deployment configuration

Use the normal `pnpm build`/`npm run build` script. It copies the version-matched PDF worker to `public/pdf.worker.min.mjs`; running `next build` directly bypasses that preparation. `pnpm dev` also copies it. Commit the dependency lockfile and `pnpm-workspace.yaml` overrides together. This workspace used pnpm 12.3.4.

Required existing settings: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, server-only `SUPABASE_SERVICE_ROLE_KEY`, and the application's site/auth redirect URLs. Worker/cron production access needs `CRON_SECRET`. Keep provider keys and service-role keys out of `NEXT_PUBLIC_*`, screenshots, and client code.

New controls:

| Setting | Behavior |
| --- | --- |
| `AI_GLOBAL_DAILY_BUDGET_USD=0` | Disable paid calls for initial staging/deployment. Unset defaults to 25; invalid/negative values deny calls. |
| `AI_GLOBAL_DAILY_BUDGET_USD=5` | Example conservative live rolling-24-hour ceiling; choose the value you intend. |
| `AI_AUTO_ESCALATE=0` | Disable automatic advanced escalation; explicit advanced requests still need the correct paid plan. |
| `AI_AUTO_ESCALATE=1` | Permit bounded escalation for eligible plans. |
| `AI_PROVIDER=google` | Explicit low-cost-first provider preference. Only configure providers you intend to use/pay for. |
| `AI_MAX_CONCURRENCY=2` | Existing queue limit; keep low during initial rollout. |

A standard attempt consumes one credit and reserves $0.75; advanced consumes five credits and reserves $2.00. A successful call with complete usage reporting settles to estimated cost. Failed/ambiguous calls keep their hold. An advanced question pass and a subsequent advanced analysis are separate calls and each consumes five credits. Auto-escalation adds five credits to the initial standard credit. Credits reset on the database calendar month (use UTC); the global ceiling is rolling 24 hours. These estimates/holds are application safeguards, not a guaranteed provider-invoice ceiling: maintain provider-side limits and reconcile usage, particularly failed/time-out requests. Do not automatically release unknown holds or grant free signup credits.

Paid activation: run `supabase/checks/activate_paid_plan.example.sql` only after replacing its placeholders and verifying payment. It is intentionally outside migrations and does nothing while placeholders remain. Team entitlements are shared; viewers cannot spend them. The usage screen currently shows the user's own consumption, not every team member's consumption. There is no live Stripe checkout/webhook in this release.

## Staging acceptance before production

1. Use separate owner/member/viewer/free accounts. Confirm viewers can read allowed reports but cannot upload, retry, coach, reanalyze, import equipment, record checks, or place pins. A guest must never reach a paid provider. Direct authenticated attempts to create an entitlement or set `is_admin` must fail.
2. With no entitlement, save a manual photo, finish a checklist, add a manual finding, and export the existing PDF/CAP/LSRA/ILSM outputs. Confirm zero provider traffic. Denied AI attempts must show a useful message and retain manual records.
3. Activate a deliberately small test entitlement. Verify standard-only Pro, advanced tier denial, expired plan denial, monthly/global caps, and a team member changed to viewer. Start with mocked/staging provider responses; any real paid call needs a deliberate test budget.
4. Import the sample CSV, then a representative real building report. Verify leading-zero IDs, building, serial, location, and equipment type. Resubmit: skipped matches must not duplicate. Explicit update must preserve check history and pins. Review PDF footers/wrapped lines before import. Scanned/image-only PDFs are not OCR-supported in this release.
5. Scan a physical Code 128 label and QR label on the actual iPhone/Android devices you support over HTTPS. Confirm a known code opens its correct building record; an unknown code prefills registration; the same barcode in another building remains separate. Headless image decoding tests do not validate every physical camera/device.
6. Upload/select a drawing, confirm an extinguisher position, scan again, and verify the saved position. Try a cross-building pin through the API: it must fail. Record pass/fail/not-tested checks and verify due-date behavior.
7. Start a scheduled occurrence twice; only one new inspection should exist. Verify fresh checklist answers and correct next date.
8. Reanalyze a photo with an assigned finding/comment/plan pin. Confirm retained IDs/links and no lost inspector work. Force a persistence failure: analysis must not falsely report success. Finalization with a queued/failed photo must be rejected.
9. Confirm the worker cron runs on the actual hosting plan, signed storage URLs work, and your existing scheduled action emails still deliver. Keep monitoring and restoration procedures separate from this code release.
